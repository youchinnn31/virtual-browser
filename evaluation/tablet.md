# タブレット実機評価の使い方

## 起動と接続

PCでリポジトリのルートから実行します。通信速度は利用者がCharlesで手動設定します。評価サーバーからCharlesを操作する設定は不要です。

```sh
npm install
npm run start:tablet
```

このコマンドはビルド・サーバー起動・接続設定・URL表示をまとめて行います。既存の評価サーバーがポート3000で起動している場合は再起動せず、そのサーバーの接続設定だけを確認します。コードや環境変数を変更した場合は、既存サーバーを停止してから実行してください。

タブレットとPCを同じLANに接続し、タブレットのブラウザで表示されたURLを開きます。

```text
http://PCのLAN内IPアドレス:3000/evaluation
```

ポート3000への接続を許可してください。Charlesを使う場合はCharlesの待受ポート（通常8888）にも端末から接続できるようにします。評価サーバーとCharlesは同じPCで動作できます。

### WindowsのWSL2で動かす場合

WSL2のNAT環境では、Windowsのlocalhostで開けても、LAN内のタブレットから直接開けない場合があります。`npm run start:tablet` は次を自動実行します。

1. Windows側の有効なLANアドレスと、現在のWSLディストリビューションのサーバーへ到達できるIPv4アドレスを取得する。
2. TCP 3000をWindows側からWSLへ転送し、同じサブネットからの受信を許可する。
3. 新しい接続先のHTTP応答を確認した後、このアプリの古いIP向けの転送・受信許可を片付ける。
4. タブレットで開くURLを表示する。

変更が必要な場合だけWindowsの管理者承認（UAC）が表示されます。設定が合っている場合は変更・管理者承認なしで接続を確認します。他アプリの転送設定は上書きせず、競合時はエラーで停止します。

Wi-Fiを変更した場合やWSLのIPが変わった場合は、サーバー起動中に次を再実行してください。IPアドレスの手入力は不要です。

```sh
npm run tablet:network
```

複数のネットワーク接続がある場合は、物理アダプターを優先し、デフォルトルートとインターフェースのメトリックが小さいLANを選びます。必要ならWindows側のインターフェース名を指定できます。

```sh
npm run tablet:network -- --interface "Wi-Fi"
npm run tablet:network -- --dry-run
```

`--dry-run` は自動検出したアドレスと更新計画を表示し、設定は変更しません。接続先の確認のため、先にサーバーを起動してください。従来の `expose-wsl.ps1 -ListenAddress ... -ConnectAddress ...` による明示指定も使えます。

更新するのは、このアプリの `VirtualBrowser-Tablet-<IP>-3000` という名前で管理している設定だけです。新しい接続先の確認に失敗した場合は、追加した転送を取り消すか元の転送先へ戻します。

これは起動時・コマンド再実行時の更新であり、Wi-Fi変更の常駐監視ではありません。ネットワークを変える前に実行中の評価を停止し、更新後のURLで新しく測定してください。ネットワーク側が端末間通信を禁止している場合は、この設定だけでは接続できません。

端末では `http://Windows側LANアドレス:3000/evaluation` を開きます。`localhost` やWSL側の内部アドレスは使いません。Charles未設定の接続確認では、端末のWi-Fiプロキシ設定を無効にして確認してください。

評価はタブレットで開いたページのJavaScriptが進めます。USB接続やPCによる実機ブラウザの遠隔操作は不要です。サーバーはタブレットのUser-AgentとCSS寸法を仮想ブラウザに設定します。仮想ブラウザのDPRは1、端末のDPRは実測値を別途保存します。

## Charlesを手動設定して測定する

評価機構は手動設定専用です。CharlesのWeb Interface・制御用設定ファイル・認証情報は不要です。旧 `CHARLES_CONFIG`・`CHARLES_CREDENTIALS` は参照しません。ページで1024kbpsを選択するだけでは、1024kbpsの回線にはなりません。

1. 画面ロックを解除し、端末の向きを固定します。キーボードを閉じてから開始してください。
2. 端末名、対象URL、測定する速度を選び、「測定開始」を押します。
3. Charlesで上下とも指定速度、追加遅延0msに手動設定し、「Charlesの手動設定を確認して続行」を押します。
4. WebSocketを再接続後、URLごとに初回収集1回＋測定5回を自動実行します。
5. 複数速度を選んだ場合は、速度が変わるごとに外部設定の確認で待機します。
6. 終了後、Excelリンクから結果を取得します。

選択速度は申告値として記録します。実効速度の自動検証や、終了時のCharles設定の変更は行いません。保存形式の `speedMode` は既存の結果との互換性のため `external-unverified` を使用します。

## 計測と結果

### ターミナル・ログファイルで処理を確認する

`npm start` と `npm run start:tablet` のどちらでも、サーバーのターミナルに `[tablet]` で始まる進捗ログを出します。同じ内容を既定で `evaluation/results/logs/tablet-server-<日時>-<PID>.jsonl` に保存します。起動時の `service-ready` に実際のファイルパスを表示します。

- `client-connected`：評価ページのWebSocket接続。
- `evaluation:speed-required`：外部の速度設定後、端末の確認ボタンを押すまで待機。本測定はまだ開始していません。
- `navigate-start` / `navigate-complete`：サーバーの仮想ブラウザによるアクセス開始・選択した待機条件の完了。待機条件・HTTPステータス・所要時間も記録。
- `navigate-failed`：ページ読み込み待ちの失敗。待機条件・所要時間・エラーを記録。
- `capture-start` / `image-queued`：画像化の開始、画像の送信キューへの追加。種類・画像ID・WebPサイズを記録。
- `client-rendered`：端末から全画像の描画完了を受信・検証。最初の画像種別と計測値を記録。
- `evaluation:trial-saved` / `excel-written`：DB保存、Excel出力。
- `candidate-skipped` / `evaluation:condition-error` / `stop-requested`：候補スキップ・処理失敗・停止理由。

`image-queued` は送信キューに入れたことを表し、端末での表示確認は `client-rendered` で行います。画像データ本体・再接続用トークン・認証情報はログへ出しません。

既存サーバーを再利用する場合、そのプロセスの標準出力は元の起動ターミナルへ出ます。ログファイルで追跡してください。古いサーバーには新しいログ処理が反映されないため、変更後はサーバーを停止し、`npm run build` と `npm start` を実行して評価ページを読み込み直してください。

```sh
tail -f evaluation/results/logs/tablet-server-*.jsonl
```

### 測定値の扱い

評価ページの「撮影開始の待機条件」で次を選択できます。通常画面の `src/server/index.ts` の設定とは別です。

| 選択肢                               | 保存値             | 待機内容                                                       |
| ------------------------------------ | ------------------ | -------------------------------------------------------------- |
| 通信が落ち着くまで待つ（従来の条件） | `networkidle2`     | 通信数が2以下の状態が500ms続くまで待機。既定値                 |
| ページの読み込み完了まで待つ         | `load`             | loadイベントまで待機。継続するfetch等の通信の静止は待たない    |
| DOMの構築完了まで待つ                | `domcontentloaded` | DOMContentLoadedイベントまで待機。画像の読み込み完了は待たない |

Yahoo等で初回画像の表示後に次のアクセスが60秒でタイムアウトする場合は、ログの `navigate-start` / `navigate-failed` を確認してください。`networkidle2` の待機が原因なら「ページの読み込み完了まで待つ」で新しい評価を開始できます。`load` も画像等が完了しなければタイムアウトします。タイムアウト時に別の条件へ自動で切り替えることはありません。

待機条件は全6アクセスで統一し、`config.json` とExcelの「測定条件」に保存します。条件を変えると撮影時点や初回収集できるLCP候補も変わるため、異なる待機条件の値は区別して比較してください。

計測するのは、端末が要求を送信する直前から、最初の受信画像を `drawImage()` でCanvasへ描画した直後までの時間です。画面への物理的な表示完了や、ブラウザ標準のLCPとは異なります。

対象サイトへのアクセスと画像化はサーバー側で行います。選択した条件の待機後に保存候補をLCP値の降順で画像化し、最後にビューポートを送ります。端末は同じ評価ページに留まり、画像を描画します。

ページ取得・候補収集・撮影は通常画面と同じ `src/server/rendering/page-renderer.ts`、画像の縮小加工は同じ `src/server/rendering/image.ts` を使用します。評価側のワーカーはブラウザとDBの準備、試行順序、終了処理を担当します。待機条件・タイムアウト・キャッシュ・画面寸法等の設定や、端末側の描画方法は別なので、通常画面との比較時にはこれらの条件も確認してください。

- 指定URL・速度ごとに新しい仮想ブラウザのコンテキストと収集用DBを作ります。
- 初回の候補と表示時間を保存し、2〜6回目には候補を追加しません。
- HTTPキャッシュは仮想ブラウザ側で無効、Service Workerはバイパスします。端末のページはno-store、画像は新規Blobです。端末全体のキャッシュを消去する機能ではありません。
- 全画像の描画とDB保存が完了するまで、次の要求を送りません。
- 候補がない、要素が消えた、非表示等の場合も理由を記録し、ビューポートを送ります。
- 5回すべて成功した場合に全5値の中央値を出します。5回とも最初の画像がLCP部分画像であれば、先行描画評価の中央値も別列に出します。

保存先は実行ごとに分かれます。

```text
evaluation/results/tablet-<時刻>-<ID>/
  config.json
  results.db
  collected/1.db
  collected/2.db
  results.xlsx
```

Excelは「中央値」「測定値」「候補処理」「測定条件」「速度設定」の5シートです。端末情報、サーバー・Chromeのバージョン、Gitコミット、速度ごとの手動設定確認履歴を記録します。Git情報を取得できない環境では `APP_REVISION`、Charlesのバージョンは `CHARLES_VERSION` で指定できます。

保存ルートは `TABLET_RESULTS_DIR` で変更できます。通常の `json.db` と既存のPCクロールの結果は実機評価には使用しません。

## 停止・エラー

「停止して保存」を押すと、進行中の試行を無効にして取得済みの結果を保存します。タブの非表示、向きや画面サイズの変更、通信切断でも停止します。Safari等で検出できる状態変化は実機によるため、画面ロック解除と前面表示を実験者側でも維持してください。

切断時は、保存が終わるまで待ってから表示されたExcelリンクで結果を取得してください。途中の試行を成功扱いにして再開する機能はありません。再実行は新しいDBになります。

サイトの処理失敗はその条件を終了して記録し、次の条件へ進みます。自動再試行はしません。5件揃わない条件の中央値は空欄です。タイムアウトはナビゲーション60秒、試行180秒です。

実行中は別の評価・通常の仮想ブラウザ操作を受け付けません。`Ctrl+C` / `SIGTERM` によるサーバー停止では進行中の評価を停止・保存して終了します。強制終了やPC停止では最後のExcel更新を保証できません。SQLiteには確定済み試行が残ります。

## 通信制限の範囲

タブレットのWi-FiプロキシにCharlesのIP・ポートを手動設定し、タブレットと評価サーバー間の画像用WebSocketがCharlesを通ることを確認してください。仮想ブラウザから対象サイトへの通信は直接接続します（Chrome起動時に `--no-proxy-server` を指定）。PC全体やルーター側での帯域制限は評価機構では設定しません。

速度ごとの確認後にWebSocketを接続し直し、その後にURLごとの初回収集と5回測定を開始します。速度の確認待ちと再接続は表示時間の計測に含めません。実行中の速度変更は行わず、次の速度の確認画面まで待ってください。

## 検証

```sh
npm run build
node --test --test-concurrency=1 evaluation/*.test.mjs
```

ローカルの固定ページとPCのChromeで、実機用ページの巡回・再接続・途中停止・保存、リダイレクト・非表示候補、既存PCクロール、速度ごとの手動確認前にアクセスしないこと、旧Charles自動制御設定が残っていても手動測定できることを検証します。ポート3000を共有するためテストは直列で実行してください。

実物のタブレットと実際のCharlesを組み合わせた検証は別途必要です。
